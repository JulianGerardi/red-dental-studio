Overview

Documentation that can’t fall out of date.

Most design systems are a copy of the product that someone has to keep in sync. Confidentally UI isn’t. Storybook imports the same components the app uses, the colors page parses the app’s stylesheet, and the Pages section mounts the real routes. When the code changes, the documentation changes with it.

I hid Storybook’s own chrome and designed a documentation site on top: a top bar with the six sections, a search, a menu per section and a consistent page for every component.

The problem

The same thing, built several ways.

Screen titles came in at 20, 24 and 36px. The appointment card of the patient overview was written by hand, and the calendar one was repeated three times in the same file. Colors were typed as hex values instead of tokens. Designers and developers needed one answer to the same question: which one do I use?

Structure6 sections

Ordered from the smallest decision to the whole screen.

    Foundations

    Colors, typography, radius and shadows, calculated by reading the app’s CSS. Each token shows its light and dark value and the class to use.

  2. 02

    Elements

    Ten standard pieces to build any screen: page header, buttons, fields, tabs, pills, cards, appointment cards, tables, navigation and the patient menu.

  3. 03

    What the code does today that departs from the standard, measured by scripts.

  6. 06

    Builder

    Where the pieces come together into new screens, by hand or described in words.

A component page

Three questions answered before anyone scrolls.

Every page follows the same order: breadcrumb, name, one sentence, and Overview, Guidelines and Code tabs. Three status cards answer what a team asks first:

  • Component · Ready when it has a playground and documented decisions.
  • Usage counted in the code, such as “Used in 10 files”, with the list of where.
  • Design with the decisions behind it, under “Why it looks like this”.

Specs are measured from the rendered component and its classes, not typed by hand.

Designed from the code

I measured the button before I designed it.

Each variant, primary, secondary, ghost, link and destructive, is the look the code already used most for that kind of action. The three sizes, 28, 32 and 36px, are the three heights the app used most.

Hover, pressed, keyboard focus (a 2px ring in the variant’s color, red for destructive), disabled and loading are solved once, in one component, instead of in every screen.

The same logic shaped the appointment cards. One appointment appears in four places, and each place gets the card that serves it: the Dashboard card carries everything needed to attend, the Patients card is compact, the patient overview has its own, and the calendar block adapts to day, week, month and phone. Same patient, same time, same status.

Search

Search in the words people actually use.

The search reads names, descriptions, examples and Spanish synonyms. Typing “turno” finds every appointment component, even though none of them is called that in the code.

Starting points sit under the search box (Buttons, Tables, Fields, Patient menu, Appointment cards, Colors), and a strip of 18 real pieces invites people to explore by clicking.

Builder · with AI

Describe a screen, get it built with the real components.

The Builder assembles screens from the app’s own components. Drag pieces onto a canvas that starts with the real sidebar and top bar, then nest them in columns, sections, tabs or modals. Layers shows the tree, Code gives the TSX with its imports, PNG exports the design and Share link compresses the whole design into the URL, with nothing uploaded to a server.

Describe goes further. Write “a patients screen with metrics, the table and today’s appointments on the right”, and it searches 379 pieces and 33 blocks and builds the screen block by block.

  • With a free Gemini key, the model streams its reasoning and can only answer with pieces from the catalog, because the response schema is limited to catalog IDs.
  • Without a key, a parser splits the sentence (commas, “and”, “to the right”, “below”), recognizes about 45 kinds of data for fields and maps words to blocks.
  • Every result can be undone, and each block keeps its alternatives so it can be swapped.
  • A privacy note in the panel asks people not to type real patient data, since prompts reach Google on the free plan.
Governance

The system tells you when the code drifts.

The Audit section shows what the code does today that departs from the standard: colors without a token, buttons, cards, fields and pills written outside the components, duplicates, missing states and documentation coverage.

  • In CI, a check reports hard-coded colors that already have a token.
  • Headers in the app detects which header each screen uses and flags the ones that differ.
  • Coverage makes “everything is documented” measurable: if a piece is missing, it shows up there.
Outcome

One answer to “which one do I use?”

The design system is published next to the app, updates itself from the code and gives designers, developers and product the same reference. The Builder turns it into a tool: a new screen starts from real components instead of a blank Figma frame.
